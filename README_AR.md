# دار البن البرازيلي

متجر عربي RTL ولوحة إدارة، مبنيان وفق اتجاه الكريمي والكراميل والبني ومرجع عبوة دار البن المرفقة. هذه نسخة تنفيذية جديدة داخل المستودع الذي كان فارغًا؛ لم تتوفر ملفات النموذج v0.1 أو ملف التسليم الأصلي لدمجها.

## التشغيل السريع

المتطلبات: **Node.js 24 أو أحدث** وnpm. لا تحتاج قاعدة بيانات خارجية للتشغيل على خادم واحد.

من مجلد المشروع:

```bash
npm ci
npm run build
npm run admin:create
npm start
```

يعمل الخادم على المنفذ `3000`. واجهة المتجر في `/`، ولوحة الإدارة في `/admin`. أوقف العملية باستخدام Ctrl+C.

للتطوير مع إعادة التحميل:

```bash
npm run dev
```

يعمل Vite على المنفذ `5173` وAPI على `3000`. لا تشغّل `npm start` و`npm run dev` معًا لأنهما يستخدمان منفذ API نفسه.

## دخول الإدارة

ينشئ `npm run admin:create` حسابًا باسم `admin` وكلمة مرور عشوائية قوية، ويحفظ بياناته للتطوير فقط في `.local/admin-access.json` بصلاحية قراءة وكتابة للمالك. الملف مستبعد من Git ومن حزمة التوزيع. لا تُنسخ كلمة المرور إلى الدردشة أو الكود أو ملفات الإعداد المشتركة. إعادة تشغيل الأمر لا تغير كلمة مرور حساب موجود.

افتح الملف محليًا لقراءة بياناتك، ثم غيّر كلمة المرور من «حسابي» واحذف نسخة بيانات الدخول الأولية عندما لا تحتاجها. الملف لا يتحدث تلقائيًا عند تغيير كلمة المرور. للحسابات الإضافية استخدم «الفريق والصلاحيات».

في الإنتاج يجب توفير `ADMIN_PASSWORD` بقيمة خاصة عبر إعدادات الخادم الآمنة، ويجب ألا تقل عن 12 حرفًا. اختياريًا يمكن توفير `ADMIN_USERNAME` و`ADMIN_NAME`. لا تُكتب كلمة المرور في سجل أو في ملف وصول محلي عندما تأتي من متغير البيئة.

- **مالك:** المنتجات والطلبات والمحتوى والإعدادات والفريق وسجل النشاط.
- **مدير عمليات:** المنتجات والطلبات وحسابه فقط. لا يستطيع تغيير إعدادات المتجر أو الحسابات.
- كلمات المرور محفوظة بصيغة scrypt، والجلسات الخادمية تنتهي بعد 12 ساعة. ملف تعريف الارتباط HttpOnly وSameSite=Strict، وSecure عند التشغيل الإنتاجي عبر HTTPS.

## الوظائف المنفذة

### المتجر

- رئيسية قابلة لتعديل النصوص والصورة وترتيب الأقسام وإظهارها أو إخفائها.
- متجر وبحث وفلاتر حسب التحميص وطريقة التحضير، ودليل مبسط للاختيار.
- صفحة المنتج بالأوزان وأسعارها والطحن والكمية والتوفر.
- سلة تستمر بعد تحديث الصفحة، وشراء دون إنشاء حساب.
- حساب الشحن حسب المنطقة وإظهار الإجمالي قبل التأكيد.
- تسجيل الطلب في قاعدة البيانات، ورقم طلب ورابط متابعة طويل غير قابل للتخمين.
- الأسعار والمخزون والشحن تُحسب على الخادم. إذا تغير الإجمالي بعد عرضه، يُطلب من العميل مراجعته قبل التأكيد.
- منع تكرار الطلب عند إعادة نفس المحاولة، وخصم المخزون داخل معاملة واحدة تمنع البيع فوق الرصيد.

### لوحة الإدارة

- ملخص الطلبات والمنتجات والمخزون المنخفض. الإيراد يشمل الطلبات الفعلية المسلّمة والمدفوعة فقط.
- إضافة وتعديل وإخفاء المنتجات، وإدارة الأوزان والأسعار والطحن والتحميص والمنتجات المميزة.
- مخزون **عبوات** مستقل لكل وزن، أو **جرامات** مشتركة لكل منتج عند التعبئة حسب الطلب.
- رفع صور JPG/PNG/WebP حتى 8 ميجابايت، وفحص محتواها وتحويلها إلى WebP على الخادم. ملفات SVG غير مقبولة.
- البحث في الطلبات، وعرض العميل والعنوان والتفاصيل، وملاحظات داخلية ومعلومات متابعة الشحنة.
- حالات الطلب: جديد ← مؤكد ← قيد التجهيز ← تم الشحن ← تم التسليم.
- الإلغاء قبل الشحن يعيد المخزون مرة واحدة. الطلب المدفوع يتطلب تسجيل رد المبلغ قبل إلغائه.
- حالة الدفع منفصلة عن حالة التوصيل. تحديث الحالة يسجل ما تم في الواقع، ولا ينفذ تحصيلًا أو رد مبلغ إلكترونيًا.
- محتوى الرئيسية، السياسات، بيانات التواصل، مناطق التوصيل ورسومها.
- حسابات وصلاحيات وتغيير كلمة المرور وسجل آخر 100 عملية إدارية.
- منع حفظ تعديل منتج قديم فوق تحديث أحدث للمخزون؛ أعد تحميل صفحة التحرير إذا ظهر تعارض.

## البيانات الحالية وما يلزم قبل البيع

المتجر يبدأ **في وضع المعاينة**، مع منتج محوج واحد مستوحى من العبوة التي أرسلها صاحب المشروع. سعر 180 جنيهًا لوزن 250 جرامًا و340 جنيهًا لوزن 500 جرام، والأرصدة ومنطقة الشحن، **أمثلة تشغيل وليست بيانات معتمدة**. لا يعني ذلك أن هذه أوزان المنتج أو أسعاره الفعلية.

الصور الجديدة في `public/images/coffee-cinematic.webp` و`coffee-tin-studio.webp` مولّدة بصريًا استنادًا إلى العبوة المرفقة، وليست الصور الأصلية للمنتج. استبدل الأصول بصور العبوات والشعار المعتمدين قبل النشر التجاري.

الواجهة محدّثة حسب الاتجاه الذي اختاره صاحب المشروع: هيرو داكن سينمائي، أقسام كريمية وأزرار ذهبية. تصنيفات التركي والإسبريسو والفلتر تعرض طرق التحضير، والمنتجات المميزة تعرض الأوزان الفعلية الموجودة في الكتالوج. اختيار وزن من الرئيسية ينتقل إلى صفحة المنتج بالوزن نفسه. تنسيق المتجر مستقل في `src/storefront-theme.css` عن لوحة الإدارة.

لتجهيز البيع:

1. أدخل المنتجات والأوزان والطحن والأسعار والمخزون الحقيقي، وارفع الصور المعتمدة، ثم ألغِ علامة «بيانات تجريبية» لكل منتج نشط.
2. اختر آلية المخزون الملائمة لكل منتج؛ أدخل الرصيد بالجرام عند استخدام البن السائب. تغيير آلية المخزون يتطلب مراجعة الأرصدة يدويًا، ولا يحوّل النظام العبوات إلى جرامات تلقائيًا.
3. احذف/عطّل منطقة التوصيل التجريبية وأضف المناطق الفعلية ورسومها ومددها.
4. أدخل وسيلة التواصل والسياسات الفعلية للشحن والاستبدال والخصوصية.
5. راجع تفعيل الدفع عند الاستلام وفق تشغيل النشاط، واختبر الطلب كاملًا، ثم غيّر وضع المتجر إلى «بيع فعلي».

الطلبات المسجلة في وضع المعاينة تظل موسومة «تجريبية» حتى بعد تغيير وضع المتجر؛ لا تُرسل منها شحنات أو تُحصّل مبالغ.

## حدود النسخة الحالية

- الدفع عند الاستلام متاح. **لا يوجد ربط إلكتروني** ببوابة دفع أو شركة شحن أو رسائل SMS/بريد.
- إدارة الاسترجاع بعد الشحن ورد الأموال الفعلي تتم تشغيليًا خارج الموقع؛ مسار إلغاء المخزون الآلي مخصص لما قبل الشحن.
- لا توجد اشتراكات أو نقاط ولاء أو كوبونات أو حسابات عملاء؛ يمكن إضافتها بعد اعتماد سياسة العمل والحاجة إليها.
- رفع الشعار المستقل والتحرير الحر لتصميم الأقسام غير متاحين من الأدمن الحالي؛ يمكن تغيير صورة الرئيسية وصور المنتجات والنصوص والأقسام الموجودة. تغيير الهوية الأساسية يتم في مكونات الواجهة.
- لم تُعتمد إعدادات الضرائب/الفوترة. الأسعار المعروضة هي أسعار المنتجات المدخلة، دون حساب ضريبة منفصلة أو إصدار فاتورة ضريبية.
- SQLite ورفع الملفات المحلي مناسبان **لعملية خادم واحدة وقرص دائم**. لا تستخدم نسخ خادم متعددة بقرص مؤقت أو مزامنة ملفات غير مضمونة؛ التوسع يحتاج نقل التخزين وقاعدة البيانات إلى خدمات مشتركة.
- لا يوجد نشر عام أو نطاق مربوط ضمن هذا التسليم. إعداد بيئة السحابة وحفظ الكود لا يساوي نشر الموقع.

## إعدادات الخادم والنشر

إعداد Render جاهز في `render.yaml`، مع [دليل النشر خطوة بخطوة](DEPLOY_RENDER_AR.md). يتطلب حساب Render وخطة مدفوعة بقرص دائم. رابط الموقع العام يصدر بعد إنشاء الخدمة؛ حفظ هذه الملفات وحده لا ينشر الموقع.

الملف `.env.example` يوثق أسماء المتغيرات فقط. لا يُحمّل `.env` تلقائيًا؛ حقن المتغيرات يتم عبر مدير العملية أو خدمة الاستضافة، أو استخدام دعم Node لملف البيئة صراحةً عند التشغيل.

| المتغير       | المعنى                                                                            |
| ------------- | --------------------------------------------------------------------------------- |
| `PORT`        | المنفذ الداخلي، الافتراضي 3000                                                    |
| `HOST`        | واجهة الاستماع، الافتراضي 0.0.0.0                                                 |
| `DATA_DIR`    | مجلد دائم خاص للقاعدة والصور، الافتراضي `./data`                                  |
| `APP_ORIGIN`  | أصل الموقع المطابق تمامًا دون مسار أو شرطة ختامية؛ يستخدم للتحقق من الطلبات       |
| `NODE_ENV`    | `production` على الخادم العام؛ يتطلب `APP_ORIGIN` يبدأ بـHTTPS                    |
| `TRUST_PROXY` | القيمة 1 فقط إذا كان الخادم خلف وكيل عكسي واحد موثوق ولا يمكن الوصول إليه مباشرةً |

لخادم إنتاج: ثبّت المتطلبات، شغّل البناء، وفر القرص الدائم وHTTPS وبيانات الإدارة الخاصة، واضبط المتغيرات، ثم شغّل `npm start` من مدير عملية يعيد تشغيله عند الحاجة. إعدادات الأصول والتحقق من المصدر يجب أن تتوافق مع نطاق الموقع الحقيقي. لا تعرض مجلد `data` أو `.local` من خادم الملفات.

نقطة فحص الجاهزية هي `GET /api/health`؛ يجب أن تعيد `status: ok` و`database: true`. اختبر كذلك كتالوج `/api/store` ودورة طلب تجريبي؛ فتح المنفذ وحده لا يثبت الجاهزية.

## النسخ الاحتياطي والاستعادة

```bash
npm run db:backup
```

ينشئ نسخة SQLite متسقة في `data/backups` باستخدام واجهة النسخ الاحتياطي للقاعدة، بما في ذلك البيانات الموجودة في WAL. انسخ كذلك مجلد `data/uploads` إلى وجهة آمنة. النسخ تتضمن بيانات عملاء وحسابات إدارية، فلا توضع في مجلد عام.

لا تستبدل قاعدة أثناء تشغيلها. للاستعادة: أوقف الخادم، احتفظ بالمجلد القديم، جهّز مجلد `DATA_DIR` جديدًا، ضع النسخة داخله باسم `dar-coffee.sqlite` وأعد مجلد `uploads`، ثم شغّل الخادم مع المسار الجديد وتحقق من البيانات. لا تخلط ملفات WAL قديمة مع القاعدة المستعادة.

## الاختبارات

```bash
npm run build
npm test
npm run test:e2e
npm audit --omit=dev --audit-level=high
```

- اختبارات API تعمل بقاعدة مؤقتة منفصلة، وتغطي الجلسات والصلاحيات والتحقق من المصدر والأسعار والشحن ومنع التكرار والمعاملات والمخزون والإلغاء ورفع الصور والتعارضات.
- اختبارات المتصفح تستخدم خادمًا مستقلًا على `4173` وقاعدة مؤقتة وحساب اختبار لا يوجد في قاعدة المتجر. تختبر الشراء وإدارة الطلب وتعديل المنتج والمحتوى والموبايل.
- في بيئة السحابة الحالية Chromium موجود في `/usr/bin/chromium`. على جهاز آخر اضبط `CHROMIUM_PATH` لمسار Chromium المثبت؛ لا يلزم تنزيل متصفح إضافي هنا.
- لقطات الواجهة الفعلية بعد اختبارات المتصفح في `.local/screenshots`، ولا تتضمن كلمات مرور.

## بنية المشروع

```text
src/                  واجهة React وTypeScript وCSS
server/               API، المصادقة، التحقق، الطلبات وقاعدة SQLite
scripts/              تشغيل التطوير، تهيئة الإدارة والنسخ الاحتياطي
tests/                اختبارات API والمتصفح
public/images/        الأصل البصري التجريبي
data/                 قاعدة وصور مرفوعة ونسخ احتياطية — مستبعد من Git
.local/               بيانات تطوير خاصة ولقطات الاختبارات — مستبعد من Git
```

استخدم النسخة الموجودة في بيئة المهمة. لا تنشئ Git worktree إضافيًا إلا بطلب صريح من صاحب المشروع.

## تحديث الهوية والمحتوى

تستخدم الواجهة عبارة «الحكاية في الفنجان»، وشعارًا مولّدًا لإعادة رسم العلامة الذهبية ذات التاج الظاهرة في صورة حساب السوشيال في `public/images/dar-logo.webp`، وليس ملف الهوية الأصلي. الهيدر يحتوي صفًا للهوية والسلة وصفًا للقائمة والبحث على الكمبيوتر، وقائمة وبحثًا قابلين للفتح على الموبايل. روابط السوشيال أرسلها صاحب المشروع؛ المعلومات المنقولة من لقطات الحسابين وعناوين الفروع موثقة في `CONTENT_SOURCES_AR.md`.

يمكن تعديل أسماء الفروع وعناوينها وتحديد الفرع الرئيسي من صفحة «محتوى الرئيسية» في الأدمن. قسم الفروع يدعم الإظهار والإخفاء والترتيب؛ روابط الخريطة تبحث بالنص ولا تعتمد على إحداثيات غير متحقق منها.

## تطوير المحتوى والتصميم مع الوكلاء

الواجهة تستخدم Cairo Variable بخط محلي للعناوين والنصوص، وأوزان قوية للعناوين والأزرار. مصدر النصوص المساعدة في `content/site-copy-ar.json`، مع بقاء حقول العنوان والحكاية والمنتجات في الأدمن قابلة للتعديل. الإعدادات الجديدة تأخذ قيمها الافتراضية من ملف المحتوى، ولا تستبدل نصوص إدارة مخصصة تلقائيًا.

مراجعات الكاتب والتسويق والمصمم موثقة في مجلد `content`. المساران الأساسيان «اختار بنّك» و«اعرف فروعنا»؛ للفروع صفحة `/branches`. بطاقة طريقة التحضير تفتح المتجر عند وجود منتجات، والدليل عند غيابها. صورة `coffee-journey.webp` توضيحية مولّدة لرحلة البن، وليست صورة مزرعة أو منشأة تابعة للبراند.

## تجربة الفنجان والأصفر

- `/quiz`: ثلاثة أسئلة عن أداة التحضير والنوع والاستخدام، مع ترشيح من المخزون المتاح ووزن قابل للاختيار؛ لا تطابق يعني عدم عرض ترشيح مضلل.
- `/learn`: ثلاث بطاقات تحضير مصورة، مع مقادير وخطوات قابلة للفتح.
- مجموعة معاينة: السادة والمحوج بأوزان 250/500 جم، وثلاث بطاقات لمشروبات الفروع منفصلة عن شراء البن.
- الأدمن يدعم إظهار وترتيب اختبار الاختيار وكروت التحضير ومشروبات الفروع. الصور مولدة مستوحاة من الصور المرفقة؛ الأسعار والأوزان مؤقتة.
- عند قاعدة بيانات قديمة لا يُضاف السادة تلقائيًا أو تُستبدل تعديلات الأدمن. بعد النسخ الاحتياطي، يستطيع المطور استدعاء `seedPreviewSada(db)` صراحة في وضع المعاينة فقط؛ الاستدعاء لا يكرر المنتج الموجود.
- `npm test` يشمل اختبارات المطابقة والمخزون بجانب API. تفاصيل المصدر في `CONTENT_SOURCES_AR.md` والمحتوى في `content/coffee-experience-ar.json`.

## التوليفة المخصصة وتحسين اختيار الفنجان

`/blend` حاسبة معاينة متاحة من المتجر والقائمة: برازيلي وكولومبي وإثيوبي، كميات بخطوات 50 جم، إجمالي الوزن والسعر والنِسَب، أوصاف عامة للطعم والقوام والحموضة، وحفظ/تحميل الوصفة على الجهاز. الأسعار والمنشأ أمثلة وليست قائمة منتجات دار البن. الحاسبة لا تنشئ طلبًا أو تضيف منتجًا غير موجود للسلة؛ ربط البيع يحتاج قائمة حبوب وأسعار معتمدة ومخزونًا وتسعيرًا خادميًا.

واجهة `/quiz` أصبحت مركزة بخطوات معنونة وإجابات محفوظة أثناء الرجوع، وأزرار ثابتة الترتيب وقريبة من الاختيارات على الموبايل. المصطلح المستخدم هو «كنكة». سيكشن طرق التحضير يستخدم كروت مصورة كبيرة والأصل `brewing-editorial.webp`. حالة الوصول إلى Pinterest موثقة في `content/BREWING_REDESIGN_AR.md`؛ لم تُنسب الصور إلى مراجع تعذر فتحها.

## استلام الطلب والأدمن

يختار العميل التوصيل أو الاستلام من فرع متاح. يتحقق الخادم من الفرع ويحفظ اسمه وعنوانه مع الطلب، ويحسب الشحن صفرًا للاستلام؛ لا يُطلب عنوان العميل في هذه الحالة. تغيير عنوان الفرع لاحقًا لا يغيّر سجل الطلب. يظهر مكان الاستلام في قائمة طلبات الأدمن وتفاصيل الطلب، ويمكن تعطيل استلام الطلبات من فرع دون إخفاء عنوانه. الطلبات القديمة تحتفظ بخيار التوصيل عند ترقية قاعدة البيانات.

رابط الإدارة غير ظاهر في واجهة الزوار؛ الإدارة الآمنة في نسخة الخادم على `/admin`. حساب محلي موجود للتطوير؛ لا تُرفع بياناته. Render يجهز اسم الدخول `admin` وكلمة مرور أولية مولدة محفوظة في إعداداته الخاصة. حساب Render والخدمة لم يُنشآ بعد، فلا يوجد رابط إدارة منشور أو طلبات عملاء حقيقية من GitHub Pages.

الهيدر صف واحد متجاوب، دون شريط المعاينة أعلى الصفحة. الفوتر يعرض `Developed by Mirai Solutions`. الهيرو يجمع العبوة الصفراء والعلبة السوداء، مع حلقة MP4 لحركة كاميرا خفيفة مدتها 10 ثوانٍ (نحو 529 KB) وزر إيقاف. تظهر صورة ثابتة عند تقليل الحركة أو توفير البيانات. الحركة أُنتجت محليًا من الصورة؛ أدوات Google/Gemini Omni لم تكن متصلة بهذه البيئة.

## التوليفة والمنيو والحركة

المتجر أول قسم بعد الهيرو، واسم القائمة «المتجر». «كوّن توليفتك» يعرض ثمانية مكونات توضيحية بصور تحميص وأوصاف القوام والحموضة. أسعار المكونات ومخزونها منتجات قابلة للتعديل في الأدمن؛ حساب الطلب على الخادم يعتمد سعر وزن ٥٠ جم، ويخصم مخزون كل مكون ويستعيده عند الإلغاء. التوليفة تدخل السلة مع الطحنة وتكمل طلب توصيل أو استلام من فرع؛ حفظ الوصفة خيار إضافي.

نسخة GitHub Pages تدعم تجربة تأكيد الطلب وحفظه على جهاز المستخدم فقط؛ لا تستقبلها لوحة الإدارة الحقيقية ولا تُرسل للخادم. النسخة Node هي التي تحفظ الطلبات وتعرضها للأدمن، وتحتاج استضافة مثل Render. المنيو الساخن والبارد مؤقت للتصميم؛ ليس قائمة أسعار معتمدة. رابط Mirai Solutions هو https://miraisolutions.net/.

الفيديو التعليمي للكنكة وGIF موجودان في public/media؛ إعادة توليدهما اختياريًا عبر `node scripts/generate-brew-motion.mjs` تتطلب Chromium وffmpeg. تشغيل الموقع لا يحتاج ffmpeg. جميع الحركات تحترم تقليل الحركة وتتيح الإيقاف.

## GitHub Pages مع بيانات مشتركة

دليل [Supabase](SUPABASE_SETUP_AR.md) يجهز قاعدة بيانات مشتركة ودخول أدمن بالبريد وكلمة مرور Supabase Auth؛ حساب SQLite المحلي مستقل ولا يصدر. `supabase/setup.sql` يجمع migration والكتالوج التجريبي، ولا يحتوي حسابات أو طلبات أو كلمات مرور. `npm run pages:supabase` يحتاج عنوان المشروع والمفتاح العام كمتغيرات Vite؛ يرفض المفاتيح السرية ولا يستبدل docs عند غياب الإعداد. النشر اليدوي **Publish Supabase storefront** يتحقق من جاهزية القاعدة وحماية الطلبات أولًا. المعاينة القديمة تبقى متاحة حتى التفعيل. الواجهة تستعمل HashRouter؛ تحديث الكتالوج كل ٣٠ ثانية والطلبات كل ١٥ ثانية في لوحة مفتوحة.

اختبارات Supabase: `node tests/supabase-browser.mjs` يفحص الواجهة باستجابات محاكاة. `SUPABASE_TEST_CONTAINER=dar-supabase-sql-test node --test tests/supabase-db.test.mjs` يفحص SQL في حاوية PostgreSQL 17 معزولة باسم مطابق، وينشئ/يحذف قاعدة اختبار فقط، وليس مشروع المستخدم. الاختبارات لا تثبت النشر الخارجي.
